# 05 — PostgreSQL Schema

PostgreSQL is the system of record for both planes. Every schema change is a
versioned Flyway migration; production schemas are never altered by hand.

## 1. Conventions

| Rule | Detail |
|------|--------|
| Primary keys | `uuid` generated by the application (`Identifiers.newId()`), never `serial`. Sequential ids leak tenant volume and invite enumeration. |
| Table prefix | Context name: `cms_`, `assets_`, `dep_`, `idp_`, `org_`, `auth_`, `bill_`, `aud_`, `anl_`, `int_`, `dom_`, `wf_`, `plat_` |
| Tenant scoping | `organization_id uuid not null` on every tenant-owned table + RLS policy |
| Timestamps | `timestamptz`, always UTC, `created_at` / `updated_at` maintained by trigger |
| Soft delete | `deleted_at timestamptz null` where a customer can undo; hard delete elsewhere |
| Enums | `text` + `check` constraint. Postgres enum types are painful to evolve. |
| JSON | `jsonb` for schema-flexible payloads (content bodies, resource specs) with `gin` indexes |
| Money | `numeric(19,4)` + explicit `currency char(3)`; never `float` |
| FKs | Only inside a context. Cross-context references are bare `uuid`. |
| Indexes | Every `organization_id` leading composite index; partial indexes for hot states |
| Naming | `snake_case`; PK `pk_<table>`, FK `fk_<table>_<target>`, index `ix_<table>_<cols>`, unique `uq_<table>_<cols>` |

## 2. Flyway layout

Migrations live in `backend/hatis-api/src/main/resources/db/migration` and are
grouped by context so a future service extraction takes its history with it.

```
db/migration/
├── V1_000__platform_core.sql          # extensions, outbox, operations, idempotency, feature flags
├── V1_001__identity.sql
├── V1_002__organization.sql
├── V1_003__authorization.sql
├── V1_004__billing.sql
├── V1_005__infrastructure.sql
├── V1_006__domains.sql
├── V1_007__assets.sql
├── V1_008__workflow.sql
├── V1_009__cms.sql
├── V1_010__deployment.sql
├── V1_011__integration.sql
├── V1_012__analytics.sql
├── V1_013__notification.sql
├── V1_014__audit.sql
└── V1_015__row_level_security.sql     # enables RLS + policies; runs last, once tables exist
```

Version numbers are `V<major>_<sequence>__<context>.sql`. A released migration is
immutable: corrections are a new migration. `spring.flyway.validate-on-migrate`
is on and CI fails if a released file's checksum changed.

Append-only: the table has `revoke update, delete on aud_audit_logs from hatis_app`

## 4. Isolation modes

| Mode | Storage | Chosen when |
|------|---------|-------------|
| `SHARED_SCHEMA` | Shared cluster, shared schema, `organization_id` + RLS | Default for Starter/Professional |
| `DEDICATED_SCHEMA` | Shared cluster, one Postgres schema per tenant | Enterprise requiring schema-level separation |
| `DEDICATED_DATABASE` | One database per tenant on a platform-managed cluster | Data residency / noisy-neighbour isolation |
| `CUSTOMER_MANAGED` | Customer's own PostgreSQL, reached through the connector | Private Enterprise / Self-managed |

`org_organizations.isolation_mode` selects the datasource at runtime
(`TenantDataSourceResolver`); the domain model is identical in all four modes.

## 5. Read models and replicas

`hatis-analytics` and the delivery read APIs run against a read replica when
`HATIS_DB_REPLICA_URL` is configured. Routing is explicit per use case
(`@ReadOnlyTransaction`), never implicit, so a write can never be sent to a
replica.
